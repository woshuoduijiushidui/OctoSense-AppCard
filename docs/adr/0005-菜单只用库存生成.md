# 菜单只用生成时的库存，差额由缺菜清单承接

#5 要求菜单优先使用库存、把不足的部分变成缺菜清单；#22 最初的 Implementation Decisions 因此允许菜单引用库存外的模拟商品候选，并写了「营养值……不在库存里时用模拟商品上的参考值」。已合并的实现是严格的 stock-only，并且 #21 把它钉成已验证事实（`docs/ai-nutrition-validation.json` 的 `native_stock_only_checks`）：`online_plan_ready`（`bundle/main.splash:3643`）的候选只遍历 `state.foods`，`save_ai_result` 只接受库存里的 `food_id`，且 `grams <= batch_grams(f)`。令人想吃但冰箱里没有的菜、以及「先有想吃的菜再决定买什么」，这一版不做（#43 的裁决 1）。缺菜清单因此不是「菜单本来就有缺口」，而是已生成菜单在批次被移除或过期后出现的差额。

**Status**: accepted

## Consequences

- 菜单的营养参考只取自库存记录（用户填写、包装数据或带溯源的 AI 估算，见 ADR 0004）；模拟商品的每 100 g 参考只用于模拟买菜的目录展示，不参与菜单核算。
- 模拟商品目录不参与菜单生成，只与派生的缺菜清单匹配。
- 自定义食材仍然只能来自库存。
- 「想吃库存外的菜」若要做，需要新增候选来源与菜单契约（#43 的方案 2／3），属于后续决策。

## Considered Options

- **允许库存外候选（#43 方案 2／3）**：符合 #22 最初的主线，但要改模型输入／输出 schema、prompt、`menu_issue`/`validate`、`模拟商品` 与菜单的耦合，以及原生 QA 的合成数据与断言，等于重做一条已验证的主线。
- **承认现状（已选）**：改规格而不是改代码，保持已验证的 stock-only 行为；代价是放弃「先有想吃的菜再决定买什么」这条叙事。
