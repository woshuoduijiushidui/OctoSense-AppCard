# AI 估算写回库存批次，但带溯源且仅作参考

已合并的 PR #21 让 `apply_nutrition_reply` 把 AI 估算写进 `state.foods[].nutrition`，并冻结进实际执行记录；设计 D5-015 写的是「估算只保存在当天菜单/执行快照，不自动反写库存批次」（#41 记录了这次冲突）。本仓库以 #21 为准：估算可以写回批次，但必须带 `source: "AI 估算"`、`basis`、`estimated_at`、`model` 溯源，并且只是参考，用户填写或包装数据优先。

**Status**: accepted

## Consequences

- 缺营养参考的批次经估算后就有参考值，菜单校验与 `nutrient_reference` 可继续；估算不改数量、保质期，也不触发库存操作。
- 批次营养参考可能来自用户填写、包装数据或 AI 估算；`source` 区分来源，界面按它标注「含 AI 估算，仅作参考」。
- 实际执行记录确认时把当时的参考复制进快照（ADR-0002）；之后重估或改库存不回溯已确认历史。
- 估算失败或名称不足时保留未知，不当作零，也不阻塞菜单生成与确认。
- 代价：批次营养字段混入了用户事实与估算，读库存的代码必须先看 `source`，不能把估算当成包装实测或数据库数值。

## Considered Options

- **估算只留菜单/执行快照（原 D5-015）**：批次保持用户录入值，但要改 `online_plan` 前的估算触发、`nutrient_reference` 的取值优先级、菜单是否可接受（`menu_issue` 要求参考完整），还要迁移已存估算；与已合并的 #21 相反。
- **写回批次 + 溯源 + 仅作参考（已选）**：沿用 #21，代码改动为零；代价是批次字段混合了事实与估算，需要靠 `source` 区分。
- **写回但标记为可覆盖 / 界面区分来源**：是已选项的界面补充，`source` 本身就是可覆盖的标记，界面据此标注，因此并入已选项。
