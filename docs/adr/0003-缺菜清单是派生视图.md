# 缺菜清单是派生视图，不是存储的数据

如果存储缺菜清单，它就成了第二个真相来源：库存一旦变化或日菜单被编辑，存下来的数量立刻失真，而它和日菜单谁说了算没有答案。因此缺菜清单每次由「日菜单需求 − 库存可用」重新计算；用户在缺菜清单上改数量，改的是日菜单的用量，清单跟着重算。

**Status**: accepted

## Consequences

- 模拟订单中的购物车是用户输入，必须存储；缺菜清单仍然不存。
- 收货数量少于订单数量时，剩余缺口自动重新出现在缺菜清单中——不需要为「未收到」单独记账。
- 只有两个位置能改变缺口：日菜单的需求量与库存的可用量。
- 代价：每次显示缺菜都需要重算，且必须保证重算结果与刚下单前看到的一致。

## Considered Options

- **存储缺菜清单**：读取更快，但需要额外规则解决「清单与日菜单冲突时以谁为准」，并且每次库存变化都要记得同步。
- **派生（已选）**：只有一个真相来源，部分收货的剩余缺口不需要额外机制。
